# Owner-first move-in and automatic Paystack TEST payouts

## Scope and decisions

This implements the user's approved TEST-only policy. A verified landlord or sublessor reports move-in after a successful booking charge and both booking agreements. The renter answers **True** or **False** from the notification inbox or booking. True authorizes a TEST payout five minutes after that fresh answer. False requires staff review. No answer stays held indefinitely. Existing held bookings require a fresh answer; historical completed releases are not rewritten.

**4 November update:** Staff lead no longer has to configure a TEST recipient for a new owner. Each verified landlord or sublessor enters and confirms their own individual M-Pesa number once in Bookings & payout review. Makao creates an active KES TEST Paystack recipient and stores only its opaque ID/fingerprint. The existing worker automatically picks up an eligible held booking, including one previously marked `DESTINATION_REQUIRED`, after this setup. Existing staff-configured destinations remain valid; the older staff route is optional, not a payout prerequisite. Initial setup is not an account-ownership verification by Paystack. No live money is enabled.

The renter still pays rent + deposit + 5% of (rent + deposit). For KSh 40,000 rent and KSh 40,000 deposit, checkout is KSh 84,000. The owner TEST transfer is KSh 80,000; KSh 4,000 remains separately recognized commission. All amounts use integer minor units and KES. There is no separate transfer of commission to a staff member or admin personal account.

These are **not live escrow or custody controls**. No real Paystack request or real-money movement was performed during implementation. A regulated custody arrangement, live-transfer approval, refund policy and two-person override workflow remain unconfirmed and unavailable. Historical references to mock escrow in existing class names describe the local TEST ledger only.

No dependencies were added. Existing Java 21 / Spring Boot 4.1.1, Spring JDBC/transactions, existing JPA repositories, PostgreSQL/Flyway, Android Kotlin/Compose/Retrofit and Play 3.0.12 are reused. Existing persistence was not converted between JDBC and JPA.

## Data, states and API contract

- `/home/hp/Desktop/makao-hub-backend/src/main/resources/db/migration/V68__owner_report_and_fresh_renter_move_in_response.sql`: adds nullable fresh-answer fields, notification booking links and response audit types. Null fresh fields explicitly mean **no authorization**, including old renter confirmations. The response check requires both agreements, an owner report and an answer not before the report. True sets the deadline to exactly answer + five minutes. False has no deadline. `protect_fresh_move_in_release()` makes a recorded answer immutable and rejects a new release before fresh True/deadline. The approved upgrade inserts one notice for already owner-reported held bookings, without changing money or historical timestamps. Removing this migration loses persistence and database-side bypass/replay protection.
- `/home/hp/Desktop/makao-hub-backend/src/main/resources/db/migration/V69__paystack_test_transfer_outbox.sql`: stores opaque recipient IDs/fingerprints and immutable transfer instructions, not bank/mobile numbers. One booking/payment has at most one instruction and one frozen reference. `protect_test_transfer_transition()` validates funded, eligible booking/recipient/amount on insertion; forbids instruction edits, illegal state transitions and attempted-history rewriting. Delete/update guards preserve audit history; browser roles have no table access. Removing these constraints permits duplicate instructions or redirected payouts. Applied migrations must not be edited.
- `/home/hp/Desktop/makao-hub-backend/src/main/resources/db/migration/V70__owner_test_destination_setup_key.sql`: adds a nullable UUID key to the immutable destination row. Older Staff-configured rows remain unchanged. New owner setup uses the key for safe replay; another key cannot replace the locked destination. Removing it breaks owner retry handling, while editing V69 would invalidate applied Flyway history.

The transfer state sequence is `QUEUED → UNKNOWN → PENDING/OTP/SUCCEEDED/FAILED/REVIEW`. UNKNOWN also represents an ambiguous network outcome. A verified success may later become REVERSED or REVIEW. FAILED, REVERSED and REVIEW do not automatically start another transfer. OTP is not success. Booking `PAID_HELD → ACTIVE` occurs only after independently verified transfer success in the same local transaction as ledger entries. A verified reversal appends compensating owner-payout entries without erasing the original release or fabricating a renter refund.

`POST /api/v1/renter/bookings/{id}/move-in/response` requires an authenticated active renter, owned booking, successful non-disputed booking payment, `Idempotency-Key`, and JSON `{"accepted":true}` or `false`. Identity comes from JWT, not the body. The booking is locked. Repeating the same answer does not duplicate audit/notifications; contradicting a recorded answer returns conflict. The old renter-first `/move-in/confirm` route returns Gone so an old client cannot imply fresh consent.

The existing owner move-in route now reports first. Owner role, verified status, ownership, listing kind, agreements and successful payment are checked. A replay creates neither a second report nor a second notification.

`POST /api/v1/admin/payments/owners/{owner}/test-recipient` requires an active Staff lead MFA session, UUID idempotency key, JSON recipientCode and `ownerDestinationConfirmed:true`. It is initial setup only. A different destination is rejected, not silently rebound; re-verification and the approved 24-hour cooling-off change workflow are not implemented by this route. The backend checks role/verification, but cannot infer recipient ownership from a code; Staff lead must check it with the owner.

The owner-first alternative is `GET`/`POST /api/v1/{landlord|sublessor}/payments/test-destination`. Global security requires the matching active role; the controller derives the owner UUID from the JWT and does not accept a client-supplied owner ID. POST requires a UUID `Idempotency-Key`, a local-format Kenyan personal M-Pesa number and `ownNumberConfirmed:true`. Only an active, verified owner may bind the initial destination. Existing binding is never overwritten. A matching retry key succeeds; another key conflicts. GET returns only `configured` and `eligible`, never a number or Paystack code. The owner-entered number is sent to Paystack over HTTPS to create a TEST recipient and is not stored in Makao's database.

## Security-critical execution walkthrough

### Provider boundary

`/home/hp/Desktop/makao-hub-backend/src/main/java/com/makaohub/backend/payment/paystack/client/PaystackTestTransferClient.java` contains the only new transfer HTTP adapter:

1. Constructors use the fixed official HTTPS API and bounded connection/read timeouts; the package-private constructor allows a mock HTTP test server. No user-provided host is followed.
2. `requireTestMode()` requires enabled payments, an `sk_test_` key and exactly the official configured base URL. A live key or alternate host fails before a request. This prevents accidental live transfers and credential exfiltration to another host.
3. `recipient()` validates the path identifier. `recipientData()` accepts only active TEST/KES recipients, positive opaque ID and supported `mobile_money` or `kepss` types. Unsupported business mobile-money types are rejected rather than guessing required fields.
   `createMpesaRecipient()` separately accepts a validated personal Kenyan number, calls Paystack's documented `POST /transferrecipient` with `mobile_money`, `MPESA` and `KES`, then rejects a response whose bank code/number, active TEST domain or currency differs. Only the opaque recipient record returns to the service. Removing these checks could bind a different recipient to an owner's payout.
4. `fingerprint()` hashes the recipient code. Only ID and hash are persisted, so mutable client-supplied payout details cannot redirect a frozen instruction. `Recipient.toString()` redacts the code.
5. `verifyCollection()` independently checks TEST domain, successful charge, exact reference, total including commission and KES. A local success label alone cannot authorize the transfer.
6. `initiate()` sends source balance, frozen reference, rent + deposit and recipient to Paystack. It validates the envelope but **never treats the POST response as settlement**. No raw provider body or exception cause is logged/returned.
7. `verify()` separately fetches the frozen transfer reference and validates TEST/KES/reference and expanded recipient. The worker then matches amount, recipient ID and fingerprint. `get()`, `validEnvelope()` and `text()` fail closed on malformed responses, use safe error codes and never echo credentials or personal details. `TransferFailure` carries only those codes; `Transfer` is an internal parsed result, never an authorization supplied by Android.

Removing any match permits the wrong currency, amount, recipient or unverified payment to become a payout. Removing the independent GET would trust an initiation response or forged callback.

### Durable worker and transaction boundaries

`/home/hp/Desktop/makao-hub-backend/src/main/java/com/makaohub/backend/payment/paystack/service/BookingTestPayoutService.java` coordinates existing repositories, JDBC, ledger, notification service and staff audit:

1. Constructor injects those existing components and the test-transfer enable flag; no hidden provider key is fetched from clients.
2. `configure()` validates the provider recipient, then uses `AdminStore.command()` for staff idempotency inside a transaction. It locks the owner, checks one active verified owner role, inserts the initial binding, audits it and rejects a changed binding. Concurrent configuration cannot overwrite a destination.
   `ownerDestinationStatus()` reads only configured/eligible booleans. `configureOwnMpesa()` checks verified role before contacting Paystack, asks the provider to create a TEST recipient, then locks and rechecks the owner in a transaction, inserts the initial immutable binding with owner identity/key and appends an audit event. `throwDestinationChange()` rejects every later destination change; this intentionally keeps re-verification and the 24-hour cooling-off out of the initial-setup path. A concurrent different-number request may create an unused TEST recipient at Paystack, but cannot alter the first bound destination or move funds. If setup fails before binding, no payout instruction is created.
3. `tick()` runs every 30 seconds while enabled/test-only. It selects eligible held True bookings, prepares them in short transactions and claims pending work. Already setup-blocked rows are revisited only after their missing prerequisite changes, so they cannot starve ready bookings; preparation-review failures require investigation rather than automatic retry. It never treats no response, False or legacy confirmation as True. The backend must be running; five minutes is eligibility, not a promise of exact-second delivery.
4. `prepare()` locks the booking and rechecks deadline, exact listing owner role, verification, successful non-disputed Paystack payment and destination. Missing configuration/verification is visible in booking status. It freezes rent + deposit, owner, payment and destination into one instruction; insert count prevents duplicate queue audit on concurrent workers. `flagPreparation()` exposes unexpected preparation errors for staff review, not a balance correction.
5. `claim()` locks the outbox row. A unique lease blocks concurrent workers. Before the first external POST, it **commits UNKNOWN and attempted_at**. A crash after sending therefore cannot cause a new POST/reference. The lease is three minutes; HTTP requests have bounded timeouts.
6. `reconcileReference()` suspends a webhook's outer transaction (`NOT_SUPPORTED`). Its claim transaction therefore commits before network access even when called by signed webhook. Unknown references do nothing. `Job` is an internal frozen instruction plus lease, not client data.
7. `mayInitiate()` rechecks eligibility, held status, exact verified owner role and collection while locked. The worker re-fetches recipient and verifies the collection before its single POST. On later UNKNOWN/PENDING/OTP checks it performs GET only, never a blind second POST.
8. Provider results must match frozen amount, ID and hash. Pending/OTP stay held. Unknown or mismatched results become REVIEW. Network uncertainty remains visible and can only reconcile the same instruction. A local invariant/finalization error becomes REVIEW and stops automatic action; no silent financial repair occurs.
9. `finish()` locks booking and outbox under the matching lease. On first verified success it marks release, appends release/settlement ledger entries, records notices, updates outbox and audit **in one transaction**. Replay cannot post ledger entries twice. Verified reversal appends compensating entries once. A provider state never directly overwrites a balance. No code here decides refunds or initiates a replacement for a failed/uncertain transfer.
10. `payment()` rejects disputed, wrong-total, non-KES or non-Paystack-referenced collections. `ownerRole()` checks active account, exactly one role and matching verified role. These are server checks, not Android booleans.

An interrupted first attempt before Paystack receives it may remain UNKNOWN/404 and require staff/provider investigation. This deliberately sacrifices automatic retry availability to prevent double credit. A destination bound to the wrong person requires investigation; this version cannot alter it. Revocation/dispute cannot recall a provider request already issued, so staff must reconcile in-flight transfers rather than claim cancellation.
