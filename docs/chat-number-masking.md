# Chat contact masking and cumulative numeric-group rule

Requirement: in renter–landlord and renter–sublessor chats, mask contact details, including individually spaced numbers and email domains; flag a message once **that sender** has sent more than five numeric groups **in that conversation**. Per the owner's decision, counts begin with new messages after this deployment. Historic masked messages are not reinterpreted.

Design: a numeric group is a contiguous run of digits (`123` is one group; `1 2 3` is three). The counter is capped at six, the only value needed to determine whether the threshold was crossed. A normal price with one or two numeric groups remains visible until the threshold. Once crossed, remaining digits in the current message are replaced with `[contact hidden]`; that message enters the existing `CONTACT_DETAILS` admin moderation queue. Earlier clean messages are not retroactively edited. Both chat flows still derive the sender from authentication and verify thread participation before changing the counter. No API contract or frontend change is required.

Files and method roles:

- `ChatContactMaskingService.java`: `mask` preserves the existing shared masking entry point for non-chat callers. `maskChat` applies email, phone, link and handle masking, then replaces any remaining numeric groups if the chat limit is exceeded; without it, spaced or split contact details can appear in messages. `countNumericGroups` counts at most six runs in the original input, so the database never needs the raw number. `replace` still emits only a safe placeholder and category. The phone expression accepts individual spaces/hyphens between digits; the email expression allows sentence-final punctuation after a domain. These changes feed both message services.
- `ChatNumericGroupCounter.java`: `exceedsLimit` chooses one of two constant SQL table names, never client input, and uses PostgreSQL's atomic upsert in the caller's transaction. The primary key separates thread and sender. It returns only whether the resulting count is over five. Removing it would allow a contact number to be assembled across messages, and a read-then-write alternative could lose counts under concurrency.
- `RentalChatMessageService.java`: the constructor injects the counter. `send` authenticates and locks the sender, verifies role/ownership and open thread, checks the client message ID before counting, rate-limits, increments the count, masks, validates and saves. An idempotent replay does not increment; a changed payload with the same ID still conflicts. The counter and message insert commit or roll back together. The existing `result` path supplies the flagged message to the chat UI and moderation queue.
- `RoommateChatMessageService.java`: the constructor injects the counter and entity manager. `send` now locks the authenticated sender before its existing role/ownership and idempotency checks, serializing simultaneous retries. `saveNewMessage` increments, masks, checks post-mask length, and saves using the existing flagged/clean constructors. `requireActiveSenderWithLock` rejects missing or inactive accounts while holding the lock. Removing these checks would permit unauthorized sends or duplicate counts.
- `V71__track_chat_numeric_groups.sql`: two new tables store capped counts, each linked to an existing chat thread and user. No existing rows are migrated or rewritten; removing the tables makes the new send paths fail rather than silently weakening moderation.
- `ChatContactMaskingServiceTest.java`: checks fully spaced and grouped phones, common and other email endings with punctuation, the nine-digit spaced example, and ordinary numeric prices.
- `ChatDeliveryIntegrationTest.java`: uses a synthetic PostgreSQL schema to verify migration, per-sender/per-chat separation, flagging, idempotent retry, conflicting replay, and outsider rejection.

Security path for each new send: authenticated principal → active-account lock → stored-thread participant/role check → open-thread check → idempotency check → atomic capped count → mask before persistence → existing flagged moderation status → commit. Any failure after the upsert rolls back the count. The raw numeric groups are not stored by this feature or included in moderation labels. Chat transport must still use TLS in deployment.

Failure modes: an invalid or too-long post-mask message returns a controlled error and rolls back its count. Existing historical messages cannot contribute to the threshold because original private text is unavailable. Pattern-based masking can yield false positives or miss obfuscated contacts; moderation remains a safeguard, not a guarantee. A public-facing explanation of this policy is RECOMMENDED for privacy transparency, but was not added to the chat UI per the request to keep it clean.
