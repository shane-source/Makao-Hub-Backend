## Contract and failure behavior

1. Existing authenticated/idempotent checkout initialization obtains the amount and reference on the server. PaystackClient optionally sends the configured HTTPS `callback_url`. Only test secret keys remain permitted.
2. Paystack may redirect the browser after checkout. GET `/payments/paystack/return` is public but performs no database/provider call and changes no payment state. Any query string is discarded using a fixed 303 redirect to the clean path.
3. The page offers an explicit Android browser intent link pinned to `com.makaohub.android`. It contains only `makaohub://payments/return`, never a reference, account, token, price or payment result.
4. Android accepts only that exact clean URI. A warm return reuses the existing Activity/ViewModels and requests an authenticated server recheck of their already stored pending payment. A cold start does not authenticate the user; sign in and open Payment history if session/payment state was lost.
5. The existing server reconciliation verifies provider status/amount/currency/reference and authorization. Only that response can grant payment success or unlock access. A forged/replayed navigation link cannot itself mark a payment paid or create another charge. Existing in-flight refreshes use the ViewModels' existing busy guards.

If the app is missing, the browser cannot handle Android intents, or the return fails, manually switch to Makao Hub and use Check Paystack payment/Payment history. A missing redirect never means payment failed. Do not pay again while pending. Already initialized checkout sessions will not acquire a newly configured callback; do not create duplicate payments to test navigation.

## Backend files and security walkthrough

- `/home/hp/Desktop/makao-hub-backend/src/main/java/com/makaohub/backend/payment/paystack/config/PaystackProperties.java`: adds the optional `checkoutReturnUrl` record component. The canonical `@ConstructorBinding` keeps Spring Boot binding deterministic despite the compatibility three-argument constructor, which leaves the URL unset. `validatedCheckoutReturnUrl()` returns null when absent; otherwise parses with `URI`, requires HTTPS, a DNS-style non-localhost hostname, standard TLS port, the exact return path and no credentials/query/fragment. Invalid configuration fails checkout initialization rather than sending an unsafe callback. This is syntactic validation, not proof of domain ownership/reachability; operators must confirm both. `toString()` is redacted to avoid accidental secret disclosure. Removing validation permits unsafe redirect configuration; removing the optional default breaks installations without hosting.
- `/home/hp/Desktop/makao-hub-backend/src/main/java/com/makaohub/backend/payment/paystack/client/PaystackClient.java`: `initialize()` retains the test-key check before callback validation and adds only the validated callback to `CheckoutRequest`. Its callback field uses `JsonProperty` and `JsonInclude.NON_NULL` so absent configuration preserves the original provider payload. Existing verify/amount/reference/provider-URL checks remain. Removing this field disconnects Paystack from the return page.
- `/home/hp/Desktop/makao-hub-backend/src/main/resources/application.yaml`: binds `MAKAO_PAYSTACK_CHECKOUT_RETURN_URL` with an empty default. No secrets/default public domain are introduced.
- `/home/hp/Desktop/makao-hub-backend/src/main/java/com/makaohub/backend/auth/config/SecurityConfig.java`: permits only GET on the exact return page. It does not expose payment/status/reconciliation APIs or POST requests. Without this rule the external browser receives 401 before it can show the button.
- `/home/hp/Desktop/makao-hub-backend/src/main/java/com/makaohub/backend/payment/paystack/api/PaystackCheckoutReturnController.java`: `page()` first chooses OK versus fixed-path 303 from the presence of a query, then applies no-store, no-referrer and a restrictive CSP. Query-bearing requests return an empty redirect, preventing reflection, open redirects and passing references to the app. The clean page is static HTML/CSS with no external resources, scripts, payment claims, account data or service dependencies. The anchor is a user-initiated, package-pinned browser intent. Removing the controller leaves Paystack's return target missing. Incoming query data can still appear in browser history or upstream proxy access logs before redirect: hosting must disable/redact query-string logging and must not load analytics/resources on this path.
