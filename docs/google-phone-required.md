# Required Google-registration phone and existing-account completion

## Outcome, requirements and undecided items

The previous Google registration path deliberately omitted the phone field. The Android payload did not include the form's number, GoogleRegistrationRequest accepted null/empty numbers, and GoogleRegistrationService stored a null ciphertext/hash pair. This was not a database save failure.

Current requirements: require a real supplied Kenyan mobile number for new Google registration; the user also approved asking existing phone-free accounts to complete their own number after sign-in. Never fabricate one, copy another account's number or replace all NULL values indiscriminately. Google ID tokens do not provide a phone claim; their canonical claims are documented at https://developers.google.com/identity/openid-connect/reference .

Google-only `password_hash` is legitimately absent: those accounts did not create a password. `avatar_object_path` is legitimately absent until an approved photo upload. Required names/email/IDs/status/timestamps retain existing constraints. A blanket NOT NULL conversion or dummy password/photo would misrepresent real account data. Existing phone-free accounts remain in the database unchanged until their authenticated owner submits a number. No migration, backfill or production-data inspection was performed. Applied V57 remains unchanged.

The profile form records a number; it does not prove possession. SMS/phone-OTP verification, how existing phone numbers may be changed, and payout-destination re-verification remain separate decisions. The new endpoint cannot change payout destinations or overwrite an existing phone. The Android completion screen is an onboarding gate, not a new blanket backend access restriction: existing endpoint authorization/verification/payment checks continue to apply. Mandatory server-wide restrictions for legacy accounts are not silently introduced.

## Design and API contract

- New accounts: selected public role → number and consent checks → Google identity verification → backend validates/protects number → transactional user/role/Google identity/legal acceptance → existing email OTP → existing role-specific verification. An email OTP does NOT verify the phone.
- Existing accounts: authenticate using the existing password/Google + email-OTP flow → load own profile → Android shows mandatory phone-completion screen for RENTER/LANDLORD/SUBLESSOR if the backend's phone is absent → authenticated POST `/api/v1/profile/me/phone/complete` with only `phoneNumber` → 204 → reread own profile → workspace only when phone is present. Sign-out remains available.
- Completion derives the user ID exclusively from the JWT subject, permits only public active roles, row-locks the own account, and checks the stored account/role again. It stores AES-GCM ciphertext and an HMAC lookup hash through existing PhoneProtectionService. The database's existing unique hash and paired-presence constraints remain the last line of defense for races. Same normalized phone replay is a no-op; a different phone on an already completed account is 409. Duplicate phone is 409; invalid input is 400; unauthenticated/invalid subject/inactive account is 401; non-public JWT roles are 403.
- Existing rate-limiter policy is reused: RECOMMENDED technical limit 10 attempts per 15 minutes per source IP for this new path, using the same mechanism as sensitive profile-role changes. This is process-local and resets/evicts like the pre-existing limiter; shared multi-replica enforcement remains necessary before scaling.
- Network failures never advance onboarding locally. A lost save response may be retried safely with the same number. The app rereads the server profile instead of inventing success, phone verification or role approval.

## Backend file and method walkthrough

All backend paths below are under `/home/hp/Desktop/makao-hub-backend/`.

1. `src/main/java/com/makaohub/backend/auth/api/GoogleRegistrationRequest.java`: the `phoneNumber` component now has `NotBlank` and the same nonempty Kenyan-mobile pattern as email registration. Omitting/null/blank/malformed phone fails HTTP validation before account creation. The Google-provided name fallback, required token/role and explicit legal consent are unchanged. Without this validation old clients could submit phone-free registration requests again.
2. `src/main/java/com/makaohub/backend/auth/service/GoogleRegistrationService.java`: `register()` keeps the existing security order. First reject public ADMIN and verify the Google token. Then check existing Google/email identity without auto-linking. Explicitly reject missing phone for non-HTTP callers too; normalize using the shared normalizer; encrypt/hash with the existing protector; reject an existing hash. Resolve the selected public role/name, persist both protection fields (no null branch), persist role/Google association/legal acceptance and begin email OTP in the transaction. Removing the service guard reopens a bypass for internal callers; bypassing the token/duplicate checks permits impersonation/duplicate accounts; skipping protection exposes contact data. No role or phone ownership is marked verified.
3. `src/main/java/com/makaohub/backend/auth/domain/User.java`: `completeMissingPhone()` refuses either already-populated protection field. It validates/copies both inputs before assigning either field, so a null argument cannot leave a partial pair and caller byte-array mutation cannot alter stored state. The existing phone-optional constructor is retained for historical accounts/tests; new Google registration no longer calls it without protection. Removing the guard enables contact changes through an initial-completion path.
4. `src/main/java/com/makaohub/backend/profile/api/CompletePhoneRequest.java`: one validated phone field only; redacted `toString()` prevents accidental representation-based phone disclosure. No target user ID, role, verification or payout fields exist. Without this contract the new authenticated route has no safe input boundary.
5. `src/main/java/com/makaohub/backend/profile/api/ProfileController.java`: `completeMissingPhone()` validates the body, extracts UUID exclusively from the authenticated JWT and forwards that ID and phone to ProfileService. It returns no phone or session in its 204 response. Supplied user IDs cannot choose another account. Removing subject extraction or accepting a caller-selected account introduces cross-user writes.
6. `src/main/java/com/makaohub/backend/profile/service/ProfileService.java`: `completeMissingPhone()` runs transactionally. `findByIdForUpdate` serializes writes for that account; missing/inactive account is rejected; exactly one stored public role is required; missing/malformed phone is rejected even for internal calls; shared normalizer/protector computes the protected pair. If an existing hash matches, return without mutation (retry); if it differs, reject rather than overwrite/reveal an existing number. Otherwise reject a hash already owned elsewhere, fill both fields and flush inside the transaction. The existing unique constraint handles different-account races that outpace the preliminary lookup. No decryption/logging/phone verification/payout changes happen here. Removing the transaction/lock risks competing account writes; removing the unique constraint permits duplicate numbers.
7. `src/main/java/com/makaohub/backend/auth/config/SecurityConfig.java`: only this new POST route requires a RENTER/LANDLORD/SUBLESSOR JWT authority. Existing JWT account/version validation still applies; ProfileService independently checks the stored account/role. Existing public registration and payment rules are untouched. Without this boundary any authenticated authority could reach the mutation controller.
8. `src/main/java/com/makaohub/backend/auth/config/AuthRateLimitFilter.java`: adds only the exact completion POST path to the existing 10-per-15-minute bucket policy, limiting repeated number probes without broad filter refactoring. Removing it permits unrestricted completion attempts at this boundary.

## Android file and method walkthrough

All Android paths below are under `/home/hp/Desktop/makao-hub-frontend/`.

1. `app/src/main/java/com/makaohub/android/data/MakaoApi.kt`: GoogleRegisterRequest includes `phoneNumber`; CompletePhoneRequest includes only the number; `completePhone()` maps the authenticated completion POST and expects a 204 response. Neither request permits target-account, payout or entitlement parameters. Removing these contracts drops the number or breaks completion.
2. `app/src/main/java/com/makaohub/android/data/AuthRepository.kt`: `completePhone()` uses the existing serialized in-memory authenticated-session/refresh path and `requireSuccess()`. Errors propagate; it does not claim phone verification or install new credentials. Removing this method loses the authenticated connection between the form and the server.
3. `app/src/main/java/com/makaohub/android/AuthViewModel.kt`: `googleRegistrationError()` checks the existing phone format and legal consent, without demanding an email/password from Google users. `googleRegister()` repeats that validation for non-UI callers, normalizes the supplied form number, sends it with the selected role and only moves to OTP on a server challenge. `phoneCompletionRequired` derives solely from the loaded public-role profile's missing phone. `completePhone()` runs only while completion is required, validates input, sends the own authenticated request and rereads the server profile; it never assigns a client-invented phone or verification state. Existing busy guards serialize taps. Removing these guards allows incorrect onboarding progress and avoidable requests.
4. `app/src/main/java/com/makaohub/android/ui/AuthScreens.kt`: RegisterScreen validates phone/consent before opening the Google chooser and passes that same number to the ViewModel. `PhoneCompletionScreen()` reuses existing Makao form components/theme, offers a phone field, Save and continue, retry-profile and sign-out actions, and clearly says storage is not verification/payout setup. It has no skip action. The draft phone is held with `remember`, not saved to disk/saved-instance state. Without this screen historical phone-free users cannot enter their own missing data.
5. `app/src/main/java/com/makaohub/android/MainActivity.kt`: the ACCOUNT branch renders PhoneCompletionScreen before constructing public-role workspaces when the authenticated profile requires it. Backend profile refresh controls exit from the screen. No new role, verification or payment privileges are granted. Without this check existing accounts bypass the Android onboarding requirement.

Existing JPA usage is retained only where already used in auth/profile; no module is moved/refactored and no new ORM dependency is introduced. Existing Spring Boot 4.1.1/Java 21, Kotlin 2.2.10, Android Gradle plugin 9.4.0 and Retrofit 3.0.0 are retained. No new library APIs/dependencies were added.

## Risks, confirmations and suggested next task

Existing missing numbers cannot be recovered without the owner's input; they remain NULL until completion. Optional password/photo values deliberately remain NULL. Old app versions will be rejected for phone-free NEW Google signup and must update; only the updated Android app enforces the new completion screen. Automatic database-wide NOT NULL is intentionally not applied while historical rows are incomplete.

No SMS verification or payout-destination change is implemented. RECOMMENDED: decide and implement phone-possession verification before treating the number as trusted for sensitive payment/contact purposes. General profile-contact audit history and multi-replica rate limits also deserve security review; the current initial completion does not log phone contents. Confirm privacy notice/data-collection purposes with Kenyan counsel before production. No new provider/escrow behavior is assumed. Suggested next task: test the new/old account flow on a connected Android device, then define the phone-verification and approved contact-change policies.
